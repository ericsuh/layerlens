  The two findings that shaped everything

  Layer cache sharing is ChainID, not the digest you see in docker pull. The
  shared trunk is the longest common prefix of rootfs.diff_ids. Using manifest
  digests — the obvious choice — would have been wrong.

  DiffID equality is too strict for "could be shared." Tar mtimes mean two
  byte-identical rebuilds normally produce different DiffIDs — which is
  precisely the phenomenon this tool exists to expose. So there's a second,
  separate identifier: a normalized changeset digest over (path, kind, content 
  sha256, mode, link target). The architecture is emphatic that the UI never
  calls that a cache hit.

  The prototype makes the demo land: v2's stray .git/ at +36.7 MiB forks the
  image, and the npm install layer below it is flagged ≈ same content —
  identical work, no longer cached.

  Everything is metadata-only: layer tars stream through once into compressed
  indexes, and no extracted filesystem ever hits disk. That's what makes 25 GiB
  tractable in ~1.5 GiB of RAM.

● Verified against BuildKit's source. This changes one of your earlier answers,
  so let me be explicit:

  Docker uses two different caches, and they have different rules:

  - Layer store (ChainID over DiffIDs) — decides if a layer is shared/skipped on
    pull. Byte-exact, mtimes included.
  - Build cache (contenthash, tarsum v1) — decides if a COPY/RUN step
    re-executes. It hashes name, mode, uid, gid, size, typeflag, linkname, 
    uname, gname, devmajor, devminor + xattrs + content, and deliberately 
    excludes mtime — the code comment says so outright.

  That maps cleanly onto our two features: the trunk is layer-store semantics,
  and "could be shared" is build-cache semantics. So I'll adopt tarsum-v1 field
  selection for both the could-be-shared digest and the tree's modified rule —
  which means uid/gid now count, reversing your earlier Q5 answer. Docker's rule
  wins, as you asked.
